# 面向用户的表达与内容交付

从读者当前想完成的事选择内容，让成稿具体、自然、有层次、能直接使用。用户最新要求和项目中的具体业务规范优先；技术设计说明保留读者需要理解的原理与取舍。

## 起草与修改

1. **先确定读者、任务和结果。** 在提纲前读取本规范，利用已有上下文明确读者关心什么、看完需要理解或完成什么；信息已足够时直接起草。委派时把本规范、读者场景、现有事实与交付目标一并交给执行者。
2. **沿内容本身组织层次。** 用户当前要用的信息在前，较深解释随后，开发排查资料放参考入口。简历沿原章节和项目展开；项目故事按责任、问题、做法、选择理由、结果与经验组织。按实际内容选结构，避免把所有材料机械分成同一套类别。减少重复与干扰，保留理解和操作所需的细节。
3. **写实际意义和可用结果。** 操作说明讲入口、操作和结果；原理解释讲方法怎样解决具体问题、为何需要它、还留下什么问题。联系已有材料先准备完整可用稿，再提示确实缺少的本人情况。保留真实按钮名称、平台来源、消息日期以及生成、保存、发送等有操作意义的状态。
4. **贴合情境表达。** 选择读者用得上的事实，解释必要术语，句子前后连贯。会改变选择或操作的条件放在对应步骤，例如确认后立即发送、修改材料下轮生效。资料里列出的限制或未提供的功能，按其是否影响当前任务与正常使用预期决定要不要写。删除不帮助判断或行动的泛泛“不保证”“由用户负责”等责任切割话术。需要解释限制时，说清具体影响和现有做法。

## 交付前复读

分别检查事实与表达：先对照实际资料和能力，再以目标读者身份连续读完受影响内容或使用流程。主代理复读委派后合并的最终稿。

- 读者能否找到当前要做的事、操作入口和操作后的结果？产品能准备的材料是否已经先给出来？
- 推荐、回复或面试答案是否回应接收者真正关心的问题？涉及关键方法时，是否解释了具体作用、选择依据和必要取舍？
- 层次是否帮助理解，段落是否顺畅？内部字段换成中文后仍难懂时，继续改成实际意义。
- 内容、数字、按钮和结果是否有依据？生成示例、合理推断与本人真实经历分清，不给产品补写尚未具备的能力。

发现问题先改，再读上下文。格式、链接、关键词和测试通过分别说明对应检查结果；内容是否好用，要根据具体成稿判断。修改规模与任务相称，已达到约定质量时完成交付。

## 情境与分工

需要核对用户原话、责任切割与必要提醒的区别、简历结构或检索机制案例时，读 [来源与案例](references/source-cases.md) 对应部分。

项目进展汇报使用 yes-prime-minister；技术问答同时需要简洁答案和教学展开时使用 reasoning-answer-crafting。各自保留用途与必要结构，共同遵循本规范的读者视角；不把用户材料改成开发验收回执。
