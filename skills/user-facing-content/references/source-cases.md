# 表达与内容交付案例

以下案例提炼自实际协作讨论，保留问题、判断理由和适用条件，已去除个人识别信息。技术机制示例用于解释方法，不作为任何人的实际工作经历。

## 1. 先判断内容对读者有什么用

**问题：** 用户指南混入大量开发核对、内部字段和泛泛的责任说明，读者难以找到自己要做的事。

**判断理由：** 内容正确还不够，还要帮助读者理解、选择或操作。开发验收记录有其用途，但通常不应占据用户主线。

**方法：** 在提纲前确定读者与当前任务，逐段判断内容的作用。必要操作信息靠近对应步骤，例如“确认发送后立即发送当前文字”；没有增加行动价值的“不保证结果、最终由用户负责”等泛泛说明可以删除。资料列出的限制按其是否影响当前任务和正常使用预期选择展示。

**范围：** 用户指南、帮助、界面文案和其他成稿。需要解释技术设计时，保留读者理解原理与取舍所需的细节。

## 2. 用内容自身的结构组织层次

**问题：** 简历编辑将所有文字挤在一处，或机械分成“基础资料”“常用资料”，与用户熟悉的简历结构不符。

**判断理由：** 用户通常按技能、工作经历、项目经历等章节查找和修改内容。沿原结构组织，更容易定位需要改善的段落。

**方法：** 使用读者熟悉的章节、项目和工作过程组织内容。项目故事可按责任、问题、做法、选择理由、结果和经验逐步讲；其他材料根据自身内容选择结构。标题、主句、段落和表格只要帮助理解，就应保留。

**范围：** 分层方式随材料和任务变化，不把某一份简历或故事的结构强制用于所有文稿。

## 3. 解释要答到关键机制

**问题：** 介绍检索项目时，只说“语义与关键词检索提供不同角度的材料”，没有说明它们分别解决什么。

**判断理由：** 接收者需要理解方法如何起作用以及为什么选择它；仅出现术语，不能证明解释已经充分。

**方法示例：** 用户问“假期怎么休”，文档写“年假管理办法”，语义检索帮助找到意思接近但措辞不同的段落；关键词检索可找到包含指定产品编号或错误码的材料。合并两路结果后，仍要处理重复和排序等问题，再确定回答采用哪些内容。

**范围：** 面试、学习和方案解释。真实面试材料还需结合本人的做法、取舍和观察结果，不能把原理示例变成已完成的工作。

## 4. 产品先准备可用材料

**问题：** 面试准备工具让用户先独立写完整项目故事，系统只在之后给建议。

**判断理由：** 已有简历足以先组织初稿；要求用户重复完成产品本可承担的整理工作，会增加使用负担。

**方法：** 利用已有简历先准备可编辑故事，用户在现成稿件上核实与补充。缺少真实决策、分工或结果时，给出具体提示。简历整理和回复准备也可按其实际能力采用这一方法。

**范围：** 产品职责和已有能力范围内的准备工作。不编造成果，也不把仅能提供建议的产品写成已具备生成或发送能力。
