# 核对项目的当前状态

## 判断框架

代码及运行证据支持实际状态，任务连接计划与实施。文档分清两类用途：当前已确认状态基线与未来变更提案；提案改变不等于实现已经改变。需要理解历史取舍时，按 C08 等主题查阅 `references/source-cases.md`，普通核对直接读取本次项目材料。

## 流程

1. 明确本次模块/项目、当前查询或修改范围、谁负责决策。定位已有权威文档、任务记录、代码与可重复运行证据。
2. 按用户功能列当前状态：设计目标、实际能力、实施任务、证据时间与对应版本/环境、差距。无法关联时分别写“代码存在”和“该版本运行待验证”，不把旧运行结果直接归给新版本。优先跟踪用户能使用的流程，而非文件数量。
3. 查最近变更及相关决策，分开历史选择、当前生效状态、未来提案。当前状态记录对应证据；提案记录依据、确认程度及变化条件。发生冲突时比较对象、范围、时间和依据，不把蓝图直接算作当前实现或当前发布缺口。
   存在多个方案时，标明正式路线、试验候选和暂未采用项。候选试验成功不等于已经切换；重新比较说明新证据或基线变化，不能每次交接都重新推荐已明确暂不采用的方案。
4. 从实际变更定位直接对应模块和文档；下游影响检查消费了哪项变化。先粗定位，再对必要部分深入，兼顾遗漏风险与检查、维护成本，不要求预先建立全部细粒度依赖。
5. 输出清楚的状态总结：现在具备什么、哪些设计仍待实现、哪些记录需更新、推荐下一步。对未验证项说明具体缺什么证据。
6. 获得更新任务时，补到现有对应文档，保存决定、理由、范围和来源；查询任务只读核对并给出差异。
7. 交接时带上目标、当前状态、关键决定及理由、角色分工、执行习惯、有效证据和下一步。

维护长期记录时按用途取舍：要求和关键决策保留可查原话，运行细节先简化，失效计划退为带时间的历史。检索围绕本次问题，不默认把所有长期资料装进每次对话。学习作答和探索假设各自标明性质。

## 产出

用一份适度简洁的状态核对记录连接相关资料。适合时用“功能—当前实现—证据—设计差距”表格；不要为了形式另建整套文档目录。

## 验收

- 每个“已实现”由代码/运行事实支撑，不只来自设计文档。
- 未来目标与当前事实分别表达。
- 旧决策保留变更依据，不与新状态混用。
- 影响范围说明实际关系；未改动的相关模块无需自动重查。
- 交接者能直接知道下一步，而非仅得到文件名单。

这是一次核对与更新方法。持续自动同步、后台索引和跨会话搜索属于系统能力，不能以写出一份记录宣称这些能力已经建成。
