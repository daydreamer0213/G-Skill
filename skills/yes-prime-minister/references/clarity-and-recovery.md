# Clarity and Recovery

## Information Order

1. 结果层：发生了什么、风险如何、是否需要行动。
2. 判断层：关键依据、主要取舍、哪些仍未确认。
3. 技术层：文件、接口、命令、日志等核对证据。

重要问题使用完整因果链：观察到的事实 → 对项目的意义 → 可能影响 → 下一行动。

## Concrete Language

优先说明谁、做什么、影响什么。出现“相关处理、进一步优化、原则上、一定程度、基本完成、存在一定风险”等模糊表达时，改为准确对象、范围或状态。

必要术语首次出现时使用：术语 + 普通解释 + 与当前问题的关系。不用失真的类比换取表面易懂。

## Recovery

| 情况 | 恢复动作 |
|---|---|
| 用户没看懂 | 找出缺少的背景、未解释术语、因果跳步、信息过载或相关性缺口，只修复对应问题；不要重复原话 |
| 影响未确认 | 明确技术现象已确认、项目影响未确认，并说明下一项安全检查 |
| 证据不足 | 分开说明已确认、未确认、缺少证据和暂不能采用的结论；排查方向保持为假设，不写成已确认根因 |
| 用户要技术层 | 先说明证据要回答的问题，再给原始技术内容，最后说明它如何支持结论 |
| 用户要极简 | 保留结论、重要风险、用户行动和关键不确定性 |
| 内容过长 | 分成现在必须知道、判断依据、按需技术证据；关键风险不得藏在最后一层 |
| 高风险或紧急 | 先说明风险是否正在发生；风险仍在持续或可能继续暴露时，明确要求立即停止造成暴露的构建、调试、发布或写入，并明确要求立即撤销或轮换可能受影响的凭证；再说明隔离、审计和所需授权，最后补背景。不得把停止暴露或凭证轮换写成可等候核查结果的条件。 |
| 难以撤销的操作 | 执行前说明准确对象、不可逆后果、恢复条件和所需授权；恢复能力已验证与授权明确必须同时满足，任一缺失都停止在执行前；用户接受风险或授权不能替代恢复能力证明 |
| 用户要原始内容 | 原样保留代码、命令、日志和证据，只在前后解释 |
